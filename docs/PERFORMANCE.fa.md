# راهنمای سرعت 1.7.33 — با حفظ ظاهر و افکت‌ها

این انتشار مسیر دریافت تصویر و فایل‌های مشترک را اصلاح می‌کند؛ طراحی، فونت، اسلایدر، autoplay، گالری هاور/لمس، زوم، درخشش و حرکت برندها حذف یا سبک‌سازی ظاهری نشده‌اند. این سند جای اجرای PageSpeed روی فروشگاه واقعی را نمی‌گیرد.

## تغییرهای داخل ZIP

### تصویر و LCP

- چهار اندازهٔ **uncropped** با عرض‌های ۹۶، ۱۶۰، ۳۲۰ و ۴۸۰ پیکسل (`jluxe-media-96` تا `jluxe-media-480`) ثبت می‌شود؛ اصل تصویر یا تنظیمات crop ووکامرس بازنویسی نمی‌شود.
- ریزعکس گالری از کوچک‌ترین candidate ثبت‌شده در metadata با نسبت طبیعی مناسب استفاده می‌کند؛ اگر اندازهٔ تازه هنوز تولید نشده باشد، از اندازهٔ موجود سازگار استفاده می‌شود. URL اندازهٔ خیالی ساخته نمی‌شود و در درخواست صفحه هیچ تبدیل تصویر یا درخواست HTTP برای بررسی فایل اجرا نمی‌شود.
- `srcset` و native `sizes="auto, …"` به ریزعکس‌ها و بنرهای معمولی اضافه شده‌اند. تصاویر lazy کارت اصلی نیز می‌توانند عرض واقعی اسلات را در مرورگر سازگار اعلام کنند؛ fallback قبلی برای مرورگرهای دیگر حفظ است. فهرست candidateها برای Retina محدود به ۹۶px یا اندازهٔ CSS نمی‌شود.
- `data-full` گالری همچنان منبع بزرگ/کامل است؛ افکت تعویض و بازگشت عکس اصلی بدون تغییر باقی می‌ماند.
- لوگوی برند اندازهٔ کوچک **هم‌نسبت** می‌گیرد؛ پویانمایی marquee، حالت خاکستری، hover و pause تغییر نمی‌کنند.
- GIFها در مسیرهای اصلاح‌شده با فایل اصلی و بدون srcset مشتق‌شده نمایش داده می‌شوند تا به فریم ثابت تبدیل نشوند. برای فرمت متحرک/تصویر art-directed دیگر می‌توان از فیلتر `jluxe_image_preserve_original` استفاده کرد. تبدیل GIF به WebP متحرک در این نسخه انجام نشده است.
- preload و رندر هیرو یک resolver مشترک دارند: attachment حذف‌شده کنار گذاشته می‌شود و fallback تصویر موبایل در هر دو مسیر یکسان است. فقط هیروی اولین بخش فعال محتوا، preload اصلی خانه را می‌گیرد؛ اگر چیدمان سفارشی دارید این انتخاب را در خروجی HTML staging بررسی کنید.
- کارت اول دیگر بالاتر از هیروی اول خانه `fetchpriority="high"` نمی‌گیرد؛ روی صفحات فروشگاه/محصول بدون آن هیرو، اولویت کارت اول حفظ می‌شود. تعداد چهار کارت eager تغییر نکرده است.
- تصویر اول هیرو و همان کارت‌های eager از `data-no-lazy="1"` استفاده می‌کنند. مسیر `LiteSpeed 7.9.1` در `src/media.cls.php` این ویژگی را در شرط bypass صریح می‌خواند؛ وجود `loading="eager"` به‌تنهایی در آن شرط نیست. این محافظ تضمین نمی‌کند که علت تأخیر ۶٫۴ ثانیه‌ای گزارش قبلی دقیقاً همین بوده باشد.

مرجع قرارداد LiteSpeed: [سورس نسخهٔ 7.9.1، شرط data-no-lazy](https://github.com/litespeedtech/lscache_wp/blob/v7.9.1/src/media.cls.php#L1053-L1063).

### JavaScript، بدون حذف اجزای رابط

فایل‌های بسیار کوچک مشترک در دو گروه React runtime و UI مشترک جمع شده‌اند. islandهای صفحهٔ ورود، محصول، فروشگاه، checkout و فوتر همچنان ورودی‌های جدا هستند؛ برنامهٔ mount و رفتار دستیار/سبد تغییر نکرده است.

فقط entry و وابستگی‌های **static** آن در head با `modulepreload` کشف می‌شوند؛ optional/page-specific islandها، دستیار و Lenis کورکورانه preload نمی‌شوند. این کار برای جلوگیری از اضافه‌شدن یک رفت‌وبرگشت «main → React» پس از جداکردن runtime است. اگر main از صف خارج شود، preload آن نیز چاپ نمی‌شود.

| سنجهٔ محلی یکسان | قبل | بعد |
|---|---:|---:|
| JSهای closure مربوط به main، Header، MiniCart، CategoryDrawer، MegaMenu، MobileNav، AiAssistant | ۳۶ | **۱۱** |
| مجموع gzip همین closure با `node:zlib` | ۱۰۵٬۰۷۷ بایت | **۱۰۰٬۷۵۱ بایت** |
| درخواست‌های JS کامپایل‌شده در fixture دسکتاپ، همراه Lenis | ۳۷ | **۱۲** |

این‌ها **اندازه و تعداد فایل محلی** هستند، نه کاهش قطعی زمان LCP/TBT فروشگاه. کوچک‌شدن فایل main به‌تنهایی به‌عنوان صرفه‌جویی گزارش نمی‌شود؛ بخش React به فایل دیگر رفته و در جمع بالا محاسبه شده است. فایل CSS کامپایل‌شده و شش فونت WOFF2 در مقایسه با 1.7.32 بایت‌به‌بایت یکسان‌اند.

## بعد از نصب: اندازه‌های تصاویر قدیمی

ثبت سایز جدید، فایل‌های رسانهٔ قدیمی را خودکار تولید نمی‌کند. دسترسی به رسانه/هاست فروشگاه در این محیط وجود ندارد و چنین کاری روی production انجام نشده است.

1. از دیتابیس و پوشهٔ uploads پشتیبان تهیه کنید و ابتدا staging را بررسی کنید.
2. چند تصویر واقعی مربع، افقی، عمودی، لوگوی شفاف و GIF را انتخاب کنید.
3. با ابزار استاندارد Regenerate Thumbnails یا WP-CLI فقط اندازه‌های لازم را بسازید؛ **اصل تصویر و اندازه‌های قدیمی را حذف نکنید**. در WP-CLI گزینه‌های مربوط به اندازه عبارت‌اند از `--image_size=jluxe-media-96` (یا 160/320/480)، `--only-missing` و `--skip-delete`. ابتدا روی IDهای منتخب واقعی تست کنید؛ اجرای گروهی روی رسانهٔ زیاد را در ساعات کم‌ترافیک انجام دهید.
4. وجود فایل‌ها و درستی metadata را بررسی کنید؛ helper به metadata وردپرس اعتماد می‌کند و برای تشخیص فایل حذف‌شده روی CDN، به هر تصویر درخواست شبکه اضافه نمی‌کند.
5. کش HTML/LiteSpeed/CDN مربوط به صفحات را پاک کنید تا srcset تازه به بازدیدکننده برسد.
6. `currentSrc` تصاویر را در عرض‌های مختلف و DPR=1/2/3 بررسی کنید. اگر مرورگر تصویر بزرگ‌ترِ ازقبل‌کش‌شده را برای ریزعکس دوباره مصرف کند، الزاماً دانلود اضافه یا خطا نیست.

بهینه‌سازی encoding تصاویر با حفظ رنگ/وضوح، و تولید WebP/AVIF متحرک با حفظ فریم‌ها، کار جداگانهٔ رسانه/هاست است؛ این ZIP فایل‌های uploads را تغییر نمی‌دهد.

## Cache TTL: بخش وابسته به هاست

هشدار `None` برای JS و `7d` برای فونت/CSS با کم‌کردن افکت یا `header()` در PHP پوسته حل نمی‌شود؛ فایل استاتیک معمولاً بدون اجرای وردپرس سرو می‌شود.

برای **پاسخ موفق فایل‌های محتوامحور/هش‌دار** زیر `wp-content/themes/zarrin/assets/compiled/assets/`، از میزبان/CDN بخواهید این سیاست را بررسی کند:

```http
Cache-Control: public, max-age=31536000, immutable
```

قیدهای ضروری:

- فقط فایل‌های واقعاً هش‌دار؛ `manifest.json`، فایل بدون هش، HTML، AJAX، REST شخصی، حساب، سبد، checkout و nonce نباید چنین کشی بگیرند.
- پاسخ خطا/404 نباید immutable یک‌ساله شود.
- فایل‌های بدون هش jQuery یا افزونه‌ها به سیاست جدا و cache-busting معتبر نیاز دارند؛ CSS/JS تولیدشدهٔ LiteSpeed خارج از پوشهٔ پوسته هم باید در تنظیمات خودش/هاست بررسی شود.
- هدر نهایی را در پاسخ واقعی مرورگر بررسی کنید؛ CDN ممکن است هدر مبدأ را جایگزین کند. MIMEهای `text/javascript` و `application/javascript` نیز باید درست پوشش داده شوند.
- نوع وب‌سرور و مجوزهای `.htaccess` در این مخزن معلوم نیست. بنابراین ZIP هیچ `.htaccess` خودکار، تغییر Nginx یا دستکاری تنظیمات LiteSpeed را تحمیل نمی‌کند.
- کش HTML لایت‌اسپید و کش مرورگر دو موضوع جدا هستند. TTL بیشتر عمدتاً برای مراجعهٔ مجدد/صفحهٔ بعد مفید است و به‌تنهایی cold-cache LCP را حل نمی‌کند.

## موارد عمداً دست‌نخورده

- jQuery/اسکریپت‌های افزونه‌ها حذف یا به‌صورت عمومی async/delay نشده‌اند. در گزارش قبلی چند فایل LiteSpeed هنوز blocking بودند؛ handle و گراف وابستگی واقعی آن‌ها باید از HTML/شبکهٔ سایت مشخص شود.
- main CSS بدون Critical CSS کامل و آزموده async نشده است؛ چنین تغییری می‌تواند FOUC و CLS ایجاد کند.
- سبد، نشست، nonce و پاسخ‌های شخصی cache عمومی نمی‌گیرند؛ درخواست اولیهٔ سبد و صحت badge برای امتیاز دستکاری نشده‌اند.
- forced reflow با برچسب `unattributed` به یک افکت خاص نسبت داده نشده؛ driver انیمیشن‌ها عوض نشده است.
- امتیاز PageSpeed، رفع قطعی تأخیر ۶٫۴ ثانیه و افزایش CWV زنده ادعا نمی‌شود.

## شواهد آزمون و کنترل پس از نصب

- تست‌های PHP: انتخاب candidate متناسب، رد crop/upscale، فایل‌های قدیمی بدون اندازهٔ تازه، GIF/opt-out، حذف attachment، preload/picture یکسان، اولویت خانه/فروشگاه، رندر واقعی قالب کارت/بنر/برند با WP/Woo doubles و preload محدود به static imports.
- تست‌های Node: بودجهٔ تعداد/حجم closure، حفظ lazy بودن ورودی‌های صفحات دیگر، به‌علاوهٔ مجموعهٔ رگرسیون قبلی.
- سناریوی جداگانه در `tests/integration/run.mjs` برای API واقعی metadata/srcset وردپرس و GIF افزوده شده است؛ تصاویرش مصنوعی‌اند و آزمون encoder یا بازتولید رسانهٔ production نیست.
- مقایسهٔ Chromium 153 با PHP واقعی پوسته، CSS/JS واقعی و دادهٔ نمایشی: شش ترکیب عرض/DPR برای قبل و بعد (۱۲ حالت)، هندسهٔ یکسان در تلورانس کمتر از یک پیکسل، بدون overflow صفحه، انتخاب تصویر کوچک برای ریزعکس غیرمشترک، تعویض/بازگشت گالری، اسلایدر، بازوبسته‌شدن سبد/دسته‌بندی/دستیار و reduced-motion. بستن سبد با دکمهٔ بستن؛ Escape برای دسته‌بندی و دستیار بررسی شد.

گزارش و اسکرین‌شات‌های محلی در `artifacts/performance-1.7.33/` هستند و در ZIP پوسته بسته‌بندی نمی‌شوند.

برای تأیید فروشگاه: پس از نصب روی staging، بازتولید اندازه‌های لازم و purge کش، حداقل سه تست موبایل هم‌شرایط بگیرید. HTML اولیه، currentSrc و preload تصویر LCP، پاسخ هدرهای استاتیک، انتخاب تنوع، افزودن به سبد، ورود، پرداخت و ظاهر موبایل/دسکتاپ را مقایسه کنید. تولید بسته یا موفقیت تست‌های نمونه به معنی deploy یا اندازه‌گیری production نیست.
