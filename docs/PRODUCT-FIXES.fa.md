# راهنمای اصلاحات محصول — 1.7.34 (R167)

این انتشار سه مشکل پیش‌فرض تنوع، بازشدن پیشنهادها پس از افزودن و نمایش/ذخیرهٔ ضمانت‌ها را اصلاح می‌کند. بهینه‌سازی‌های تصویر و بسته‌بندی R166 حفظ شده‌اند؛ روی فروشگاه واقعی نصب یا تنظیمی اعمال نشده است.

## تغییر سیاست در 1.7.35 (R168)

طبق درخواست جدید مالک، انتخاب اولیه **همیشه اولین تنوع فعال، قابل‌خرید و موجود به ترتیب menu_order/ID ووکامرس** است؛ پیش‌فرض ذخیره‌شدهٔ روی تنوع بعدی دیگر آن را جلو نمی‌اندازد. اگر اولی ناموجود باشد، دومی/سومی بررسی می‌شود؛ اگر هیچ مورد قابل‌خریدی نباشد، انتخاب خالی و وضعیت ناموجود است. ذخیرهٔ پیش‌فرض در تغییر محصول/موجودی نیز با همین سیاست همگام می‌شود. انتخاب بعدی مشتری یا reset در مرورگر به‌زور بازنویسی نمی‌شود. توضیح بخش زیر مربوط به رفتار 1.7.34 پیش از این درخواست جدید است.

کارت‌های «ادامه خرید شما»، نشانگر موجودی صفحه و پیام درخواست اطلاع از موجودی، برای محصول متغیر از عرضهٔ واقعیِ تنوع‌ها استفاده می‌کنند، نه `_stock_status` کهنهٔ والد. یک عدد موجودی کافی است؛ وضعیت فعال/قابل‌خرید، حداقل تعداد، backorder ووکامرس و مخفی/خصوصی‌بودن محصول دور زده نمی‌شود. پاسخ تاریخچه no-store و برای LiteSpeed صریحاً no-cache است.

برای جستجو، فهرست نتایج از wheel/touch اسکرول Lenis مستثنا شده و اسکرول بومی داخل پنل است؛ در دو انتهای فهرست یا فهرست کوتاه، چرخ موس به صفحه نشت نمی‌کند. هدر به stacking context بالاتر از cp3-nav رفته؛ ظاهر شیشه‌ای و اسکرول نرمِ بیرون پنل حفظ‌اند. ارتفاع پنل با viewport/کیبورد و عرض موبایل با عرض واقعی هدر هماهنگ می‌شود. فوکوس لینک‌ها، Escape و تایپ مجدد نیز حفظ شده‌اند.

پس از نصب، یک بار کش HTML/CSS/JS و REST قبلی LiteSpeed/CDN را پاک کنید. این انتشار روی production نصب نشده است.

## ۱. انتخاب پیش‌فرض ووکامرس

- انتخاب خودکار قدیمی JavaScript که اولین تنوع موجود را با کلیک مصنوعی جایگزین انتخاب مدیر می‌کرد حذف شد. مرجع پیش‌فرض همچنان مقدار معتبر حل‌شدهٔ PHP/WooCommerce است.
- نام ویژگی فارسی/encode‌شده هنگام خواندن defaults، options و stock در هر دو layout به همان کلید `sanitize_title` ووکامرس نگاشت می‌شود؛ نام نمایشی با کلید ذخیره‌سازی اشتباه گرفته نمی‌شود.
- خطای واقعی `optionValues is not defined` در کنترل گزینه‌های چیدمان کلاسیک رفع شد. map دسترس‌پذیری اکنون بین دو مرحلهٔ مدرن/کلاسیک مشترک است؛ تنوع غیرقابل‌خرید یا غیرفعال نیز انتخاب‌پذیر جلوه نمی‌کند.
- سواچ/قرص از مقدار select واقعی sync می‌شود، از جمله رویدادهای jQuery ووکامرس و فرم‌های AJAX. پس از «پاک کردن انتخاب»، گزینهٔ اول دوباره خودکار کلیک نمی‌شود.
- قانون قبلی «پیش‌فرض معتبر، قابل‌خرید و موجود؛ وگرنه fallback موجود» عوض نشده است. هیچ تنوع ناموجودی به‌زور خریدنی نشده و انتخاب کاربر به variation ID متفاوت فرستاده نمی‌شود.

آزمون مرورگر واحد از کنترلر **واقعی WooCommerce 11.1.2** استفاده می‌کند: دو ظاهر، اجرای زود/دیر اسکریپت تم و حالت inline/AJAX؛ پیش‌فرض غیرِاول، شناسهٔ تنوع، تغییر انتخاب و reset بررسی می‌شوند. fixture GPL صرفاً تست است و توسط پوسته به‌جای اسکریپت ووکامرس enqueue نمی‌شود.

## ۲. پاپ‌آپ پیشنهادها بعد از افزودن موفق

- پاپ‌آپ در هر دو عرض موبایل و دسکتاپ به‌صورت خودکار و **فقط بعد از پاسخ موفق افزودن** باز می‌شود؛ کلیک دوم روی «دیدن پیشنهادها» لازم نیست.
- فرم اصلی و انتخاب سریع تنوع از یک رویداد موفقیت استفاده می‌کنند. picker قبل از بازکردن پیشنهادها بسته می‌شود تا backdrop یا قفل اسکرول با مودال بعدی تداخل نکند.
- اگر WooCommerce استاندارد در گرید `added_to_cart` بدهد ولی HTML پیشنهاد نداشته باشد، یک **خواندن `op=get`** با context محصول انجام می‌شود. درخواست افزودن دوباره ارسال نمی‌شود. پاسخ پیشنهادها شخصی/تازه و non-cacheable باقی می‌ماند.
- از داخل پیشنهادها پاپ‌آپ به‌صورت بازگشتی دوباره باز نمی‌شود؛ لغو یا خطای picker رفتار قبلی بازگشت به انتخاب‌ها را حفظ می‌کند.
- پیام موفقیت، روی دکمه‌های شیت نمی‌افتد؛ توست در مسیر دارای پاپ‌آپ پوشانندهٔ آن نمی‌شود. فوکوس، Escape، بستن، تلهٔ Tab و scroll lock همان ابزار مشترک را دارند. قبل از جایگزینی DOM مودال، focus trap قبلی آزاد می‌شود.
- پاسخ قدیمیِ پیشنهادها نمی‌تواند پیشنهاد تازه‌تر را جایگزین کند. «ادامه خرید/بستن» در زمان انتظار، بازشدن دیرهنگام را لغو می‌کند ولی snapshot سبد هنوز به‌روزرسانی می‌شود.
- خطای شبکه، موجودی یا عدم موفقیت، پاپ‌آپ موفقیت نشان نمی‌دهد. double-submit فرم اصلی/انتخاب سریع مهار می‌شود.

**تنظیمات محترم‌اند:** کلید «پاپ‌آپ محصولات پیشنهادی» همان محصول نباید خاموش باشد؛ فهرست/حالت پیشنهادها از «زرین ← اضافه خرید» می‌آید. اگر پیشنهاد معتبر وجود نداشته باشد، حالت خالیِ صادقانه نمایش داده می‌شود؛ کالای ساختگی یا ناموجود پیشنهاد نمی‌شود.

## ۳. اصالت و ضمانت در هر دو چیدمان

مسیر جدید در ویرایش کلاسیک ووکامرس:

**ویرایش محصول ← اطلاعات محصول ← گزینه‌های زرین**

سه کنترل در این تب‌اند: «گارانتی اصالت کالا»، «کالای دارای ضمانت» و «پاپ‌آپ محصولات پیشنهادی». این تب داخل General شرطی ووکامرس نیست؛ برای محصول ساده و متغیر قابل دسترسی است. کل General برای محصول متغیر به‌زور باز نشده است.

- همان کلیدهای متای قبلی حفظ شده‌اند؛ دادهٔ ذخیره‌شده مهاجرت مخرب ندارد.
- ذخیره از hook شیء محصول ووکامرس انجام می‌شود، با presence marker، nonce اختصاصی و مجوز ویرایش. نبودن چک‌باکس فقط وقتی معنی «خاموش» دارد که پنل واقعاً ارسال شده باشد؛ ذخیرهٔ موجودی، REST، bulk و درخواست بدون پنل تیک‌ها را پاک نمی‌کند.
- نمایش badge در هر دو layout از یک renderer سمت PHP است. چیدمان classic قبلاً آن را اصلاً فراخوانی نمی‌کرد.
- **فقط گزینه‌های تیک‌خورده** نمایش می‌یابند. این نسخه برای محصول فاقد ضمانت/اصالت، ادعای خودکار نمی‌سازد.

## LiteSpeed

قراردادها با سورس **LiteSpeed Cache 7.9.1** بررسی شده‌اند:

- `data-no-optimize="1"` روی زنجیرهٔ ضروری خرید: jQuery/migrate، BlockUI، wp-util/underscore، کنترلر تنوع ووکامرس، افزودن استاندارد، helper و کنترلر خرید تم؛ تنظیمات inline مرتبط نیز محافظت می‌شوند. اسکریپت inline چیدمان کلاسیک هم دیر به اولین تعامل موکول نمی‌شود.
- ترتیب dependency رسمی و `defer` بومی وردپرس حفظ می‌شود. کنترلر تم صریحاً به کنترلر تنوع وابسته است تا picker قبل از آماده‌بودن آن ساخته نشود.
- این **استثنای محدود** است، نه خاموش‌کردن JS optimization/page cache کل سایت. ممکن است فایل ضروریِ تم به‌جای نسخهٔ ترکیب/Minifyشدهٔ LiteSpeed مستقیماً دریافت شود؛ قابلیت خرید نباید قربانی Delay نامناسب شود. CSS و bundleهای مشترک R166 عوض نشده‌اند.
- پس از ذخیرهٔ واقعی محصول/تنوع، action رسمی `litespeed_purge_post` برای محصول یا والد تنوع درخواست می‌شود؛ `purge_all` خودکار نداریم.
- اگر nonce کش‌شده رد شود، کلاینت فقط برای **HTTP 403 با کد `jluxe_cart_invalid_nonce` قبل از هر mutation** یک بار نشست/nonce تازه می‌گیرد. timeout، JSON خراب، خطای موجودی و خطاهای عمومی دوباره به‌عنوان افزودن اجرا نمی‌شوند.

### بعد از نصب روی staging

1. ابتدا backup؛ ZIP جدید را نصب کنید. یک بار کش HTML و فایل‌های بهینه‌شدهٔ CSS/JS لایت‌اسپید را پاک کنید. اگر CDN جدا دارید، صفحهٔ محصول و فایل‌های قدیمی مرتبط را آنجا هم بررسی کنید.
2. صفحهٔ ویرایش محصول را تازه باز کنید؛ در «گزینه‌های زرین» موارد لازم را تیک بزنید و محصول را ذخیره کنید. checkbox قدیمی داخل صفحهٔ بازمانده از قبلِ آپدیت، پنل جدید/nonce جدید ندارد.
3. در بخش «تنوع‌ها»، یک پیش‌فرض معتبر و موجود انتخاب و محصول را ذخیره کنید. صفحهٔ محصول را در پنجرهٔ ناشناس، موبایل و دسکتاپ بررسی کنید.
4. بدون کلیک اولیه روی صفحه، پیش‌فرض باید از HTML دیده شود. افزودن موفق باید پاپ‌آپ بیاورد؛ خطا یا خاموش‌بودن تنظیم محصول نباید آن را باز کند.
5. ناموجودی، تغییر رنگ/سایز، reset، افزودن پیشنهاد، بستن/بازکردن، badgeها و تعداد واقعی سبد را بررسی کنید. اگر هنوز فایل قدیمی LiteSpeed در Network دیده می‌شود، نتیجهٔ View Source و خطای Console برای تشخیص مرحلهٔ بعد لازم است.

## مرز آزمون

تست‌های Node/JSDOM شامل کنترلر واقعی تنوع ووکامرس، سناریوهای popup و retry امن هستند. تست‌های PHP ایزوله ذخیره/نمایش/نام فارسی و قرارداد LiteSpeed را می‌پوشانند. تست مستقل `tests/woocommerce/product-regressions.php` برای WordPress 7.0 + WooCommerce 11.1.2 + MySQL/PHP 8.3 در CI اضافه شده است تا CRUD، قالب‌های واقعی و افزودن/خواندن پیشنهادها را نیز بررسی کند.

پیش‌نمایش Chromium از PHP helperها، CSS/JS واقعی و داده/پاسخ AJAX نمایشی استفاده می‌کند. این سنجش، نصب production، درگاه/SMS واقعی، سرور LiteSpeed واقعی یا اندازه‌گیری جدید PageSpeed نیست.
