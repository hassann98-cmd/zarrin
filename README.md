# پوستهٔ زرین — Zarrin

پوستهٔ کلاسیک وردپرس/WooCommerce با رابط فارسی RTL و جزیره‌های React. مبنای بازسازی پوسته **1.64.20** است؛ نسخهٔ این بستهٔ اصلاحی **1.7.35** است.

**R168:** اسکرول/لایه‌بندی نتایج جستجو اصلاح شده و سیاست جدید انتخاب اولیه، «اولین تنوع موجود به ترتیب ووکامرس» است. موجودی تاریخچه از تنوع‌ها خوانده می‌شود، نه فقط flag والد. [راهنمای رفتار جاری و پاک‌سازی کش](docs/PRODUCT-FIXES.fa.md).

**R167 — اصلاحات محصول:** پیش‌فرض تنوع، پاپ‌آپ خودکار پس از افزودن موفق و badgeهای اصالت/ضمانت در هر دو چیدمان اصلاح شده‌اند. کنترل‌ها در «ویرایش محصول ← اطلاعات محصول ← گزینه‌های زرین» هستند. برای نصب و پاک‌سازی کش LiteSpeed، [راهنمای اصلاحات محصول](docs/PRODUCT-FIXES.fa.md) را ببینید.

**بهینه‌سازی R166:** دریافت responsive ریزعکس‌ها/بنرها/لوگوها، اندازه‌های uncropped، preload هماهنگ هیرو و بسته‌بندی کم‌درخواست‌تر JS، بدون حذف طراحی و افکت‌ها. پس از نصب، رسانهٔ قدیمی و TTL هاست به مرحلهٔ جدا نیاز دارند؛ [راهنمای نصب و کنترل سرعت](docs/PERFORMANCE.fa.md) را بخوانید. هیچ بهبود CWV زنده یا deploy خودکار ادعا نمی‌شود.

> نصب روی فروشگاه فعال فقط بعد از backup و تست staging. وردپرس واقعی فقط در محیط دورریختنی PHP-WASM/SQLite تست شده؛ WooCommerce نصب‌شده، MySQL، درگاه و provider واقعی در این آزمون وجود ندارند. تست‌های مخزن جای خرید سرتاسری را نمی‌گیرند.

## پیش‌نیازها

- حداقل‌های اعلام‌شدهٔ پوسته: **WordPress 6.0 و PHP 8.0**. این اعداد تأیید سازگاری تمام نسخه‌های ترکیبی نیستند؛ PHP 8.0 نیز برای سرور عمومی انتخاب به‌روز توصیه‌شده‌ای نیست. نسخهٔ پشتیبانی‌شدهٔ PHP هاست را پس از تست انتخاب کنید.
- WooCommerce فعال و برگه‌های معتبر حساب، سبد و پرداخت. این پوسته برای **checkout کلاسیک** نوشته شده؛ Cart/Checkout Blocks تأیید نشده‌اند.
- برای توسعه: **Node >=22.12** و npm. برای `npm run check`، PHP CLI دارای tokenizer، mbstring و PDO SQLite؛ برای بسته‌سازی، Python 3 و Git.
- Node و ابزارهای تست روی هاست وردپرس لازم نیستند، اگر بستهٔ ساخته‌شده را نصب کنید.

# یا همهٔ موارد بالا به‌جز نصب وابستگی‌ها:

### آزمون یکپارچهٔ اختیاری وردپرس

این مجموعه وابستگی مستقل دارد: **Node >=24.18 و npm >=11.16**، Python 3 و `gh`. Node 22.12+ برای build معمول همچنان کافی است. از ریشهٔ مخزن و با ابزارهای نسخهٔ بالا:

```sh
npm ci --prefix tests/integration --ignore-scripts
npm --prefix tests/integration run prepare:fixtures
npm run test:integration
ZARRIN_TEST_PHP=8.5 npm run test:integration
```

۴۹ کنترل در WordPress 6.9 واقعی و دیتابیس موقت SQLite روی PHP-WASM 8.3.33/8.5.10 پاس شده‌اند. cookie، nonce، role/capability، options و REST واقعی‌اند؛ ارسال SMS شبیه‌سازی و mail/شبکه مسدود است. این مجموعه WooCommerce یا خرید واقعی را اجرا نمی‌کند. [جزئیات و روش بازتولید](docs/INTEGRATION.fa.md).

### بستهٔ نصب و به‌روزرسانی لینک دانلود

برای هر تغییرِ تحویلی، سرور دانلود sandbox را روی یک پورتِ آزاد و تازه (طبق محدودیت‌های همان نشست) اجرا کنید؛ پورت پیش‌فرض ثابت نیست تا آدرسِ یک انتشارِ قدیمی دوباره استفاده نشود. سرور روی `0.0.0.0` گوش می‌دهد و فهرست را از ZIPهای واقعیِ `downloads/` به‌علاوهٔ آرشیوهای عمومیِ ثبت‌شده در `release-history.json` می‌سازد.

ترمینال اول، با پورت آزاد همان نشست (نمونهٔ این انتشار: `4216`؛ برای انتشار بعدی پورت تازه انتخاب کنید):

```sh
PORT=4216 node scripts/theme-download-server.mjs
```

پس از آماده‌شدن سرور، ترمینال دوم (همان پورت را مشخص کنید):

```sh
THEME_DOWNLOAD_SERVER_PORT=4216 npm run release
```

`npm run release` شمارهٔ patch را خودکار افزایش می‌دهد، نسخه‌های `package.json`/lock/style/README را هماهنگ می‌کند، `npm run check` را اجرا می‌کند، ZIP نسخه‌دار می‌سازد و همان ZIP را در `downloads/` نگه می‌دارد. سرور در هر درخواست این پوشه را دوباره می‌خواند: صفحهٔ اصلی و `/releases.json` همهٔ نسخه‌های موجود را فهرست می‌کنند و `/download/<version>` هر بسته را جداگانه می‌فرستد؛ `/download/latest` همیشه نسخهٔ جاری است. release علاوه بر `/version`، حضور نسخهٔ تازه در فهرست و byte-match مسیرهای latest و versioned را بررسی می‌کند. ZIPهای قدیمی را از `downloads/` پاک نکنید، وگرنه از فهرست حذف می‌شوند.

خروجی در `artifacts/zarrin-{version}.zip` است، با پوشهٔ بالایی `zarrin/`. ZIP شامل runtime، سورس و ابزارهای بازسازی است؛ `.git`، `node_modules`، محیط/credentialها و artifactهای قبلی بسته‌بندی نمی‌شوند. `npm run package` فقط ابزار بسته‌بندی سطح پایین است و نسخه را افزایش نمی‌دهد. سرور sandbox به‌معنی انتشار روی production نیست.

`.github/workflows/quality.yml` build، تست، تطبیق خروجی با فایل‌های ثبت‌شده و ZIP را تعریف می‌کند؛ PHP matrix آن 8.0/8.3/8.5 است. job جداگانهٔ WordPress/SQLite، Node 24 و PHP-WASM 8.3/8.5 دارد. اضافه‌شدن workflow به معنی مشاهدهٔ اجرای موفق GitHub Actions نیست.

## ساختار منبع و محدودیت بازیابی

```text
functions.php                  bootstrap و بارگذاری assetها
inc/                           منطق PHP و تنظیمات
woocommerce/                   overrideهای قالب کلاسیک WooCommerce
src/main.js                    راه‌اندازی جزیره‌ها
src/islands/                   اجزای React؛ AuthPage.jsx بازنویسی خوانا دارد
src/lib/                       مسیرها، نشست REST، سبد، مودال و بازیابی خطای جزیره‌ها
src/styles/storefront.css      CSS قابل‌ویرایش بازیابی‌شده
assets/js/                     اسکریپت‌های کلاسیک و helper مشترک
assets/compiled/               خروجی قابل‌استقرار Vite
scripts/ و tests/              کنترل کیفیت و بسته‌سازی
```

**سورس اصلی TSX/Tailwind در مخزن نبود.** فایل‌های قابل‌ویرایش از bundle موجود بازیابی و importها با وابستگی‌های npm جایگزین شدند. این کار بازیابی دقیق نام متغیرها، کامنت‌ها یا تنظیمات اصلی TypeScript/Tailwind نیست؛ فهرست منشأ در `docs/FRONTEND-RECOVERY.json` است.

- build جدید از `src/main.js` انجام می‌شود؛ هیچ bundle hashed قدیمی را دستی patch نکنید.
- شکست import یا render جزیره، لینک بومی ورود/سبد/فروشگاه را نگه می‌دارد؛ شکست Lenis نباید جزیره‌های دیگر را متوقف کند.
- CSS فعلاً منبع صریح است، نه Tailwind JIT. افزودن یک utility جدید به markup به‌تنهایی CSS تولید نمی‌کند؛ استایل لازم را در منبع CSS بنویسید یا بعداً pipeline اصلی را با تست برگردانید.
- جزیره‌های `*-demo` حفظ شده‌اند و جای checkout/product واقعی WooCommerce را نمی‌گیرند.
- `dist/` قدیمی (۴۶ فایل، ~۹۶۱KB، باقی‌ماندهٔ کامیتِ اولیه) از پروژه و بستهٔ انتشار حذف شد؛ داراییِ واقعیِ runtime همان `assets/compiled/` است (از `manifest.json`). نسخهٔ قدیمی در تاریخچهٔ گیت و در شاخهٔ `main` بایگانی است.

## راه‌اندازی روی وردپرس

1. از کد فعلی، دیتابیس و uploads نسخهٔ پشتیبان بگیرید؛ ابتدا روی staging کار کنید.
2. WooCommerce را فعال و صفحات آن را تنظیم کنید. در صورت نیاز به UI این پوسته، سبد/پرداخت از shortcodeهای کلاسیک `[woocommerce_cart]` و `[woocommerce_checkout]` استفاده کنند، نه Blocks.
3. پوشهٔ کامل پوسته/ZIP را نصب کنید؛ در production، `JLUXE_DEV` خاموش یا تعریف‌نشده باشد.
4. از تنظیمات زرین، هویت، رنگ‌ها، اطلاعات تماس، حمل/پرداخت و آدرس‌ها را بازبینی کنید.
5. برگه‌های راهنما/پیگیری دیگر خودکار منتشر نمی‌شوند. اقدام اختیاریِ پیشخوان فقط **پیش‌نویس‌های ناموجود** را می‌سازد؛ محتوای واقعی و حقوقی را بازبینی و سپس منتشر کنید.
6. ویرایش/import کد CSS/JS و مجوز script/onclick در نمادهای فوتر به `unfiltered_html` نیاز دارد؛ صرف `manage_options` کافی نیست.
7. فعال‌بودن نظرات و بازبودن آن‌ها برای هر محصول را خود مدیر تعیین می‌کند؛ پوسته آن تنظیمات را به `yes` بازنویسی نمی‌کند. نظر محصول همچنان برای تأیید مدیر نگه داشته می‌شود.
8. کش صفحه/CDN را پاک کنید و چک‌لیست [اصلاحات](docs/FIXES.fa.md#۴-موارد-لازم-پیش-از-انتشار) را اجرا کنید.

### مسیرها

URLهای WooCommerce و REST از سرور می‌آیند؛ نصب زیرپوشه و `?rest_route=` در helperها پشتیبانی می‌شوند. مقدار خالی در پنل آدرس‌ها یعنی مسیر واقعی WooCommerce. تنظیمات سفارشی ورود، داشبورد، سفارش‌ها، پیگیری و صفحهٔ تشکر اکنون استفاده می‌شوند.

**نکتهٔ ارتقا:** مقادیر قدیمی `/sign`، `/account` و `/account?tab=orders` قبلاً در بعضی مسیرها نادیده گرفته می‌شدند. اگر route واقعی ندارند، آن‌ها را خالی کنید. این patch برای جلوگیری از پاک‌کردن انتخاب احتمالی مدیر، URL ذخیره‌شده را خودسرانه مهاجرت نمی‌دهد.

### قرارداد قیمت

از **1.55.4**، نمایشِ قیمت همیشه «عدد، بعد نماد/واحد» است — «۱٬۰۰۰ ریال»، نه «ریال ۱٬۰۰۰» — در فروشگاه، سبد، مینی‌کارت و پیگیری. این فقط ترتیبِ نمایش است؛ واحدِ ذخیره‌سازی همچنان همان تنظیمِ ووکامرس است.

همهٔ مبلغ‌ها و فیلتر قیمت در واحد ذخیره‌سازی انتخاب‌شدهٔ WooCommerce هستند: IRR = ریال، IRT = تومان. پوسته در فیلتر یا پیگیری، ضرب/تقسیم خودکار ۱۰ انجام نمی‌دهد و قیمت‌های دیتابیس را تغییر نمی‌دهد. اگر افزونهٔ دیگری واحد نمایشی/ارز را تبدیل می‌کند، رفتار نهایی باید با یک قیمت واقعی در staging بررسی شود.

### ورود و پیامک

- ثبت‌نام جدید تابع گزینهٔ ثبت‌نام صفحهٔ حساب WooCommerce است؛ بدون Woo از `users_can_register` وردپرس پیروی می‌کند. غیرفعال‌بودن ثبت‌نام، ورود حساب موجود را نمی‌بندد.
- رمز ثبت‌نام جدید حداقل **۱۲ نویسه** است؛ رمزهای حساب‌های موجود خودکار تغییر نمی‌کنند.
- OTP: **۶ رقم، ۱۲۰ ثانیه، حداکثر ۵ خطا**. ارسال: ۱۰ درخواست/IP و ۳ درخواست/شماره در ۱۰ دقیقه؛ تأیید: ۳۰/IP و ۱۰/شماره در ۱۰ دقیقه. ارسال ناموفق نیز بودجه را مصرف می‌کند.
- شماره‌های پشتیبانی‌شده موبایل ایرانی‌اند؛ ارقام فارسی/عربی و شکل‌های معمول پیشوند پذیرفته می‌شوند. پترن سرویس پیامکی باید کد ۶ رقمی را بپذیرد.
- OTP در WordPress Multisite عمداً غیرفعال است تا نقش مدیریتی در سایت دیگر شبکه، از مسیر مشتری دور زده نشود؛ مجوزدهی بین‌سایتی در این نسخه پیاده نشده است.
- حساب مدیریتی/پرسنلی با OTP وارد نمی‌شود. شمارهٔ صورتحساب به‌تنهایی شناسهٔ معتبر ورود نیست؛ مشتری موجود ابتدا با رمز وارد و در **جزئیات حساب** شماره را تأیید می‌کند.
- حساب OTP جدید ایمیل ساختگی ندارد؛ کاربر برای بازیابی ایمیلی، ایمیل معتبرش را در حساب تکمیل کند.
- کلیدهای کاوه‌نگار/ملی‌پیامک فقط در پیشخوان وارد شوند؛ در فایل، Git یا چت قرار ندهید. این مخزن هیچ credential واقعی لازم ندارد.
- پشت CDN، IP واقعی را با trusted proxy configuration وب‌سرور تنظیم کنید. اعتماد مستقیم به هدر قابل‌جعل `X-Forwarded-For` راه‌حل امنی نیست.

### نظرات و هوش مصنوعی

اتصال GapGPT با هر دو آدرس رسمی مستندات کار می‌کند: `api.gapgpt.app` (اصلی) و در قطعِ آن — مثلاً هاست خارج از ایران — `api.gapapi.com` (CDN خارجی) به‌صورت خودکار و یک‌بار امتحان می‌شود؛ خطای HTTP (کلید/اعتبار) سوییچ نمی‌کند. خطای نهایی نام هر دو آدرس و علت واقعی (مثل cURL timeout) را نشان می‌دهد و timeout تماس ۶۰ ثانیه است. مدل را از صفحهٔ مدل‌های GapGPT انتخاب کنید (مثل `gpt-4o`، `gemini-2.5-pro`، `gapgpt-qwen-3.6`)؛ endpoint همان `chat/completions` رسمی است.

فراخوانیِ GapGPT/OpenAI طبق مستنداتِ رسمیِ Chat Completions است؛ برای مدل‌های استدلالی (o-series و gpt-5) خودکار از `max_completion_tokens` استفاده و `temperature` حذف می‌شود. خطای کلید/نرخِ سرویس با پیامِ روشن در دستیار دیده و شرحِ کامل در debug log می‌رود. تماسِ واقعیِ پرداختی فقط با کلیدِ خودتان روی staging تست شود.

- تولید خلاصه هنگام بازشدن صفحه درخواست خارجی نمی‌فرستد. cache خوانده و کار Cron صف‌بندی می‌شود؛ در cache miss ممکن است تا اجرای Cron کارتی نمایش داده نشود.
- فقط نظرهای تأییدشدهٔ محصول عمومی وارد خلاصه می‌شوند؛ تعداد/طول ورودی محدود است. نام نویسنده، ایمیل و IP متادیتای نظر به provider فرستاده نمی‌شوند؛ خود متن عمومی ممکن است حاوی اطلاعاتی باشد که نویسنده نوشته است.
- سقف پیش‌فرض تلاش ساخت خلاصه برای کل سایت ۲۰ در ساعت است؛ فیلتر `jluxe_review_summary_hourly_limit` برای سیاست متفاوت وجود دارد. هزینه و قرارداد حریم خصوصی provider را بررسی کنید.
- میانگین معیارها در batchهای حداکثر ۱۰۰تایی محاسبه می‌شود. ویرایش، moderation و حذف، cache را باطل می‌کند. Cron غیرفعال به معنی تکمیل‌نشدن این کارهاست.

### پاسخ خودکار و خلاصهٔ دیدگاه‌ها (از 1.55.6)

صفحهٔ **پنل زرین → دیدگاه‌ها (AI)** دو قابلیت اختیاری اضافه می‌کند که هر دو به‌صورت پیش‌فرض خاموش‌اند و از همان سرویس/کلید دستیار چت استفاده می‌کنند:

- **پاسخ خودکار**: هر بار اجرا (بازهٔ ۱ تا ۶۰ دقیقه)، به دیدگاه‌های تأییدشدهٔ بی‌پاسخِ محصولات عمومی یک پاسخ کوتاه می‌دهد. سقف هر اجرا (پیش‌فرض ۵) و ۳ خطای پیاپی سرویس جلوی حلقهٔ هزینه را می‌گیرد. پاسخ‌ها همیشه با برچشفِ «پاسخ خودکار فروشگاه (هوش مصنوعی)» نمایش داده می‌شوند و آواتار اختصاصی می‌گیرند. مدل مجاز نیست قیمت/موجودی/زمان تحویل حدس بزند.
- **خلاصهٔ قابل‌ویرایش هر محصول**: متاباکس «خلاصه دیدگاه‌ها (AI)» در ویرایش محصول؛ متنِ دستیِ شما همیشه بر تولید خودکار مقدم است و خالی‌گذاشتنِ کادر محصول را به تولید خودکار برمی‌گرداند. دکمهٔ «ساخت خلاصه برای محصولاتِ بدون خلاصه» هر کلیک حداکثر ۱۰ محصول را پردازش می‌کند.
- **زمان‌بندی**: رویداد Cron فقط وقتی قابلیتی فعال باشد ثبت می‌ماند و با غیرفعال‌کردن، پاک می‌شود؛ اگر `DISABLE_WP_CRON` تعریف شده، Cron واقعی سرور را تنظیم کنید. تست اتصال و پردازش دستی از دکمه‌های همان صفحه‌اند (هر سه با nonce و `manage_options`).


### طراحی، دسترس‌پذیری و سرعت (از 1.55.8)

- **فونت فروشگاه** IRANYekan است (self-host، `font-display: swap`، preload دو وزن اصلی)؛ سیستم دکمهٔ `.jluxe-btn` و هدف لمسیِ ≥۴۴px موبایل طبق Apple HIG/Material.
- **رنگ‌ها** با محاسبهٔ عددیِ کنتراست WCAG 2.1 AA تنظیم می‌شوند — تست `R35` جفت‌های توکن را می‌سنجد و تغییر رنگ بدون به‌روزرسانیِ آن نمی‌گذرد.
- آیکون‌ها SVG درون‌خطی‌اند (`jluxe_icon()`)؛ صفحهٔ ۴۰۴ مسیر بازگشت/جست‌وجو/پیشنهاد محصول دارد؛ نوارِ چسبانِ افزودن به سبد فقط در موبایلِ صفحهٔ محصول ظاهر می‌شود و کلیکش همان دکمهٔ رسمی ووکامرس است.
- افکت‌ها فقط transform/opacity با گارد `prefers-reduced-motion`؛ بخش دیدگاه‌ها با `content-visibility` از رندر اولیه خارج است.
- **بخشِ دیدگاه‌ها (از 1.55.10):** کارتِ سفیدِ ۲۲px با سایهٔ نرم، هر نظر در کارتِ فرورفتهٔ جدا با آواتار/نشانِ خریدار/ستاره، فرمِ دو ستونه با ورودی‌های ۴۸px — طبق زبانِ طراحیِ مرجعِ صاحبِ سایت.
- **صفحهٔ محصول کلاسیک (از 1.55.11):** بازسازیِ مطابقِ DOM مرجع — کارتِ سه‌ستونه با گالریِ زوم‌دار و تامبنیل، قرص‌های تنوع متصل به select واقعی ووکامرس، پنلِ مشخصات با هشدارِ موجودی، نوارِ چسبانِ بخش‌ها با scrollspy، rate-card امتیازها از دادهٔ واقعی دیدگاه‌ها، FAQ و گریدِ محصولات مرتبط.
- **دقتِ پیکسلیِ صفحهٔ محصول (از 1.55.12):** مطابقِ اسکرین‌شات‌های مرجع — قلبِ علاقه‌مندیِ خطّی زیر عنوان، جعبهٔ خریدِ چسبان هنگام اسکرول، دکمهٔ گردِ افزودن با آیکون +، شماره‌های قرمزِ سادهٔ سکشن‌ها، مقدارِ جدولِ مشخصات چسبیده به لبه، میله‌های امتیاز راست و پنلِ کرمِ نمره چپ، کارتِ AI با آیکونِ چپ و زیرعنوانِ «تولید شده با هوش مصنوعی»، تب‌های مرتب‌سازیِ دیدگاه‌ها (جدیدترین/بیشترین/کمترین امتیاز بر متای واقعی ووکامرس) و FAQ با پنلِ داخلیِ خاکستری.
- **مودالِ اضافه خرید (از 1.55.13):** بعد از افزودن به سبد در صفحهٔ محصول، ورقِ مرجع باز می‌شود — خلاصهٔ محصول با قیمتِ خط‌خورده و درصدِ تخفیف، «این محصولات را هم اضافه کنید» با ردیف‌های انتخابیِ چک‌باکسی، جمعِ زندهٔ «مبلغ قابل پرداخت» و دکمهٔ تأیید که فقط شناسه‌ها را به endpoint واقعیِ سبد می‌فرستد. پنل زرین ← اضافه خرید: کلید فعال‌سازی، حالتِ منبعِ پیشنهاد (ثابت با انتخاب سراسری / هر محصول با Cross-sells واقعی ووکامرس / هر دسته) و خدماتِ قابل‌انتخاب (مثل بیمه) با محلِ نمایش و انتخابِ خودکار — مبلغِ خدمت همیشه از تنظیماتِ سرور خوانده می‌شود و به‌شکلِ فِیِ استانداردِ ووکامرس به سفارش می‌نشیند.
- **رفعِ خرابی‌های گزارش‌شدهٔ صفحهٔ محصول و آدرس‌ها (از 1.55.14):** قرص‌های تنوع دیگر نامکِ (slug) ترم را نشان نمی‌دهند — نامِ واقعیِ ترم از خودِ تاکسونومی خوانده می‌شود؛ گزینه‌های بدونِ تنوعِ واقعی از قرص‌ها حذف می‌شوند (کلیکِ بی‌اثر نداریم)؛ دکمهٔ گردِ افزودن به سبد با `!important` از استایل‌های ID-دارِ ووکامرس پیروی نمی‌کند و ردیفِ تعداد/دکمهٔ محصولاتِ متغیر درست چیده می‌شود (حالتِ انتخاب‌نشده با خاکستریِ disable مشخص است). صفحهٔ جدید «پنل زرین ← تشخیص سایت» وضعیتِ واقعیِ برگه‌های فروشگاه/سبد/تسویه/حساب/بلاگ و شمارشِ محصولات را نشان می‌دهد و با یک کلیک، برگه‌های ناقص را ترمیم می‌کند (فقط با کلیکِ ادمین؛ هرگز در درخواستِ فرانت‌اند چیزی ساخته نمی‌شود).
- **حسِ اپ در موبایل:** متای `theme-color` (رنگ کروم مرورگر هم‌رنگ فروشگاه)، ورودی‌های 16px (بدون زومِ خودکار iOS)، نوار چسبانِ خریدِ چیدمان کلاسیک که بالای ناوبریِ پایین می‌نشیند، پنل‌های لایه‌باز با اسکرولِ مهارشده و اسکرولِ نرم.

### cache و حریم خصوصی

نام/ایمیل کاربر در تنظیمات cacheable HTML قرار نمی‌گیرد؛ دستیار از endpoint خصوصی نشست، nonce و هویت تازه می‌گیرد. بااین‌حال **CDN و page cache باید جداگانه درست تنظیم شوند**:

- bypass کوکی‌های `wordpress_logged_in_*`، `wp_woocommerce_session_*`، `woocommerce_items_in_cart` و `woocommerce_cart_hash`؛
- استثناکردن URLهای واقعی حساب، سبد، پرداخت، REST و `wp-admin/admin-ajax.php`؛
- جلوگیری از cache عمومی پاسخ پیگیری و از ثبت body حاوی رمز/تلفن در ابزارهای logging؛
- پاک‌سازی HTML قدیمی پس از ارتقا تا UI قدیمی OTP/assetها باقی نماند.

از **1.55.2**، پاسخ‌های REST اختصاصی پوسته، شامل ورود/OTP/گفتگو/تیکت/پیگیری و خطاهای validation/authentication، `private, no-store` هستند. این هدر جای تنظیم CDN را نمی‌گیرد.

### تغییر قرارداد پیگیری در 1.55.2

- مسیر `/jluxe/v1/order-track` فقط **POST** می‌پذیرد؛ GET قدیمی دیگر پاسخ سفارش نمی‌دهد. ورودی‌ها `order_number` و `phone` در body هستند.
- تطبیق شماره سفارش و موبایل فقط **وضعیت/تاریخ/روند سفارش** را می‌دهد (`data.access = status_only`)؛ نام، نشانی، اقلام، مبلغ، روش پرداخت و کد مرسوله در این خروجی نیستند.
- جزئیات کامل علاوه بر این تطبیق، به **هویت احراز‌شدهٔ وردپرسِ کاربری که customer_id سفارش متعلق به اوست** نیاز دارد؛ رابط وب این هویت را با cookie و REST nonce تأمین می‌کند (`data.access = owner`). ورود کاربر دیگر یا customer_id صفرِ سفارش مهمان، اثبات مالکیت نیست.
- مشتری مهمان برای جزئیات باید از مسیر پشتیبانی فروشگاه استفاده کند؛ تا طراحی یک روش قویِ اثبات مالکیت مهمان، تطبیق موبایل/شماره به‌تنهایی کافی نیست. این تغییر رفتاری را پیش از ارتقا در روند خدمات مشتری لحاظ کنید.
- کلاینت پیگیری nonce را از bootstrap خصوصی می‌گیرد، شماره را در localStorage نگه نمی‌دارد و نتیجهٔ خصوصی را هنگام `pagehide` پاک می‌کند. تاریخچهٔ قدیمی همان کلید نیز پاک می‌شود.
- «تکمیل» WooCommerce و ثبت کد مرسوله به معنی اثبات تحویل فیزیکی نیست؛ UI دیگر آن‌ها را تحویل قطعی معرفی نمی‌کند.

مصرف‌کنندگان مستقیم GET یا خروجی قدیمی باید مهاجرت کنند. **HTML و assetهای CDN را پس از ارتقا purge کنید.** دورهٔ نگهداری log و اطلاع‌رسانی به خریداران همچنان به سیاست فروشگاه نیاز دارد.

### ظاهر صفحهٔ محصول

چیدمانِ صفحهٔ محصول از پنل انتخاب می‌شود: **پنل زرین → صفحهٔ محصول → چیدمان صفحهٔ محصول**. «پیش‌فرض» همان نمای سه‌ستونهٔ گالری‌بزرگ است؛ «کلاسیک» نمای ساده‌تر با ذره‌بین. اگر صفحهٔ محصول ناگهان ساده شده، اول همین تنظیم را چک کنید (مقدارِ ذخیره‌شدهٔ قدیمی ممکن است «کلاسیک» باشد)، ذخیره کنید و کش/CDN را پاک کنید.

از **1.55.5**، برای تشخیص سریع، عنصر ریشهٔ صفحهٔ محصول `data-jluxe-layout="default|classic"` دارد؛ در DevTools یا View Source همین ویژگی نشان می‌دهد کدام چیدمان واقعاً رندر شده است.

### سبد و درخواست‌های تکراری

از **1.55.3**، بعد از هر افزودن/تغییر تعداد در مسیر اختصاصی، موجودی با `check_cart_item_stock` ووکامرس دوباره بازبینی می‌شود؛ در صورت شکست (مثلاً رزرو موجودی توسط سفارش دیگری)، فقط نوشتنِ همان درخواست پس گرفته و خطای ۴۰۹ نمایش داده می‌شود. این بازبینی روی مسیر استاندارد فرم ووکامرس اضافه نشده است.

مینی‌سبد React فقط خطای مشخص nonce را یک بار، پس از bootstrap تازه، تکرار می‌کند؛ timeout، خطای JSON، 5xx یا رد موجودی خودکار تکرار نمی‌شوند. refresh مشترک header/drawer/mobile برای هر رویداد فقط یک درخواست دارد. این کار یک تراکنش سراسری بین تب‌ها، callbackهای افزونه‌ها یا مسیرهای checkout نیست.

در درخواست اختصاصی `jluxe_cart`، فیلد فرم بومی `add-to-cart` قبل از `wp_loaded` اولویت ۲۰ حذف می‌شود تا form handler ووکامرس پیش از nonce/validation مسیر AJAX عمل نکند. دو فرم کلاسیک هم آن فیلد را فقط از **payload AJAX** حذف می‌کنند، نه از DOM فرم بومی. تازگی nonce فرم‌های کلاسیک/variation picker و تعامل افزونه‌های فیلد محصول همچنان باید در staging بررسی شود.

## توسعه با HMR

Vite فقط assetها را ارائه می‌کند؛ جای سرور PHP/WordPress نیست. WordPress باید جداگانه در دسترس باشد. روی محیط HTTPS/proxy، آدرس‌های مرورگرپسند واقعی را جایگزین مثال کنید:

```sh
JLUXE_VITE_PUBLIC_URL=https://5173-YOUR-SANDBOX.e2b.app \
JLUXE_DEV_ORIGIN=https://80-YOUR-SANDBOX.e2b.app \
npm run dev
```

فقط در `wp-config.php` محیط توسعه:

```php
define( 'JLUXE_DEV', true );
define( 'JLUXE_VITE_DEV_SERVER', 'https://5173-YOUR-SANDBOX.e2b.app' );
```

سرور روی `0.0.0.0` bind می‌شود. برای میزبان دیگر، متغیرهای بالا origin/HMR را تنظیم می‌کنند. `WP_DEBUG` به‌تنهایی dev mode را فعال نمی‌کند. در مرورگر کاربر از `localhost` برای دسترسی به سرویس sandbox استفاده نکنید.

## rollback و دامنهٔ تأیید

- بستهٔ قبلی و backup دیتابیس را پیش از ارتقا نگه دارید. برای rollback، **کل پوشهٔ همان نسخه** را برگردانید و cacheها را پاک کنید؛ فقط یک فایل hashed را جابه‌جا نکنید.
- import تنظیمات یک backup محدود در option به نام `jluxe_theme_settings_before_import` می‌گذارد. این جای backup کامل دیتابیس نیست و API keyها را شامل نمی‌شود.
- افزونه‌های CAPTCHA، عضویت و فیلد اجباری محصول/ثبت‌نام باید با UI سفارشی نیز تست شوند؛ اجرای درست validation ممکن است نیاز به تکمیل اتصال فیلدهای آن افزونه‌ها داشته باشد.
- سازگاری ۲۳ override با نسخهٔ نصب‌شده، ارسال واقعی SMS/ایمیل، پرداخت، حمل/مالیات، session هم‌زمان، Woo Blocks، چندارزی و چندسایتی نیازمند محیط واقعی‌اند.
- آزمون‌های ایزوله و آزمون WordPress/SQLite واقعی اجرا شده‌اند؛ نه Lighthouse، نه خرید WooCommerce/مرورگر واقعی و نه آزمایش provider واقعی. دامنهٔ هر مجموعه در گزارش تست جدا شده است.
- دربارهٔ مجوز فونت IRANYekan و LICENSE کد اختصاصی، مدارک مالک باید تکمیل شوند. [یادداشت وابستگی‌های ثالث](docs/THIRD-PARTY-NOTICES.md) مجوزی برای فونت یا کل پوسته اعطا نمی‌کند.
